# Contributing to Maestro

Thank you for your interest in contributing. This document covers the basic development flow during the v0.1 release.

## Setup

```bash
pnpm install           # install dependencies across all workspaces
pnpm build             # build all packages via tsup
pnpm test              # Vitest in each package
pnpm typecheck         # tsc --noEmit in each package
pnpm lint              # ESLint + strict rules
pnpm format:check      # verify code formatting with Prettier
```

Requirements:

- Node.js >= 20 (LTS 24 recommended; it is the default target for builds)
- pnpm >= 9 (the repo pins via `packageManager` in `package.json`)

## Flow of a PR

1. Open a branch from `main` following the pattern `lucassampaiodegois1/<dsft-id>-<slug>` (the name generated by Linear will work).
2. Make small, descriptive commits. We use Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:` etc.).
3. Ensure that `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass before opening the PR. The CI will run all of them automatically.
4. **Add a changeset** if the change affects any publishable package (see below).
5. Open the PR pointing to `main`. Link to the Linear issue (e.g., Refs DSFT-###).

## Changesets

We use [Changesets](https://github.com/changesets/changesets) for versioning and automated changelogs.

### When to add

Whenever the change affects observable behavior or the public API of any `@maestro/*` package. For internal changes (test refactor, docs that do not affect users, CI tweaks), it is not necessary.

If in doubt, add one.

### How to add

```bash
pnpm changeset
```

The interactive CLI will:

1. Ask which packages were affected — mark with <space>.
2. Ask for the bump type for each: `patch` (fix), `minor` (feature compatibility), `major` (breaking change).
3. Ask for a short description in natural language.

It generates a file at `.changeset/<random-id>.md`. Commit this file along with the rest of the PR.

### Linked packages

During v0.1, all `@maestro/*` packages are linked: any bump propagates the same version to all. This simplifies the first release and avoids version misalignment while the product is still unstable. In v0.2+ we can separate release cycles by package.

### Release

- `pnpm version-packages` consumes pending changesets, bumps versions and generates `CHANGELOG.md` per package.
- `pnpm release` runs `pnpm build` and publishes on npm with `changeset publish`.

The process typically runs via [changesets/action](https://github.com/changesets/action) in CI (the release.yml workflow will be added in DSFT-98).

## Code style

- **Strict TypeScript.** Avoid `any`, `as unknown as ...` and non-null assertions (`!`) in production code.
- **ESM-only.** Imports must use `.js` extensions in relative paths (the tsconfig uses `moduleResolution: bundler`, but we prefer explicit for compatibility).
- **No redundant comments.** Comment the reasoning and trade-offs, not what the code is doing.
- **No `console.log` in final code.** Use the logger when available (post DSFT-78).

For details on why each decision was made, read the document [Maestro — Fundamentals and Architecture](https://linear.app/dreamsoft/document/maestro-fundamento-e-arquitetura-e571aac5d90f) on Linear.

## Reporting issues

During v0.1 the official issue tracker is Linear (Dreamsoft team, Maestro project). Open issues with enough context to reproduce: command run, `maestro --version`, Node version, operating system, relevant logs.

On GitHub, the templates in `.github/ISSUE_TEMPLATE/` serve as entry points for reports from outside the team. PRs use the template in `.github/PULL_REQUEST_TEMPLATE.md`.

## Code of Conduct

This project adheres to the [Contributor Covenant 2.1](https://www.contributor-covenant.org/version/2/1/code_of_conduct/). In short:

- Treat everyone with respect. We do not tolerate discrimination, harassment or hostility.
- Technical discussions are about code and decisions — not people.
- Report violations to `lucas.gois@dreamsoft.dev` (private). We will not retaliate against anyone reporting in good faith.

The full text of the Contributor Covenant 2.1 applies even if it is not duplicated here. If there is a conflict, the official version at https://www.contributor-covenant.org/version/2/1/code_of_conduct/ is authoritative.
